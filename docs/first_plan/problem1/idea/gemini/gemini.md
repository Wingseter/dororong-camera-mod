# Problem 1 (1600x1200 Upscaling) Analysis & Solutions

본 문서는 `README.md`의 현상 및 Trial 1 실패 분석을 바탕으로 작성된 해결(Troubleshooting) 아이디어입니다.

## 1. 실패 원인 (Trial 1 Brick)에 대한 심층 분석
문서에 정리된 실패 원인 후보들은 모두 합리적이나, 가장 가능성 높은 원인은 **"버퍼 크기 매칭 오류(Memory Corruption)"**과 **"SD 업그레이드 무결성 체크(Checksum/Bootloader)"**입니다.

1. **버퍼 크기 오류**: 버퍼 할당(`0x1C764`, `0x1C870`)까지 한꺼번에 1280으로 줄인 경우, 카메라의 센서(ISP) 동작은 여전히 1600x1200을 출력하여 버퍼에 쓰려고 할 수 있습니다. 이 경우 **Memory Overflow**로 인해 다른 힙 메모리를 침범하고 카메라가 Crash(Brick) 될 가능성이 매우 높습니다.
2. **ARM 인코딩 재확인**:
   * `MOV R4, #1280`은 `0xC05` (5 ROR 24)도 맞지만, 원본 코드의 Mode 3 에서는 `0xE50` (0x50 ROR 28 = 1280)을 사용하고 있습니다. 컴파일러가 생성한 `E50` 값을 사용하는 것이 구조적으로 더 안전할 수 있습니다. (`MOV R5, #720`인 `0xE2D` 인코딩은 정확합니다.)

## 2. 해결 아이디어 및 우선순위 제안

### 🥇 최우선 추천: 접근 B (Mode 3 강제 선택)
명령어 상수를 직접 패치하는 것보다, **이미 내장된 "Mode 3 (Native 1280)" 로직을 타도록 분기(Branch) 명령어를 조작하는 것**이 시스템 레벨에서 가장 우아하고 안전합니다.

* **아이디어 B-1: 레지스터 비교(CMP) 명령어 스와핑**
  ```arm
  ; 패치 전
  0x1FDD0: E3500002    CMP R0, #2
  0x1FDD4: 03A04E64    MOVEQ R4, #0x640 (1600)
  ...
  0x1FDE0: E3500003    CMP R0, #3
  ```
  카메라가 Mode 2로 진입할 때 1600x1200 처리가 무시되고 1280 기능의 조건문이 통과되도록 바꿉니다.
  * `0x1FDD0`을 `E35000FF (CMP R0, #255)` 등으로 변경해 분기 회피
  * `0x1FDE0`을 `E3500002 (CMP R0, #2)` 로 변경하여 통과
  * **전제조건**: Ghidra 분석을 통해 Mode 3 분기 블록 내부에 Width(1280) 외에도 Height가 정상적으로 할당되고 나머지 ISP 파이프라인 처리가 준비되어 있는지 확인이 선행되어야 합니다.

### 🥈 대안 추천: 분리 패치 및 CH341A 직접 쓰기 (접근 A + C)
여러 곳을 한 번에 패치하면 실패 지점을 알 수 없으니 통제된 격리 실험이 필수입니다. CH341A(플래시롬) 직접 쓰기는 SD 우회로써 Checksum 오류 검증을 배제할 수 있습니다.

* **1단계 (기능 분리 최소 패치)**: 버퍼 할당 코드 유지, 인코더 입력부(`0x1FDD4`, `0x1FDD8`) **딱 2곳만 패치**. 
  * 메모리가 넉넉하게 잡힌 1600x1200 버퍼에 1280x720 프레임 이미지만큼만 JPEG 인코딩하도록 속입니다. 
  * 부작용: Pitch/Stride(메모리 너비간격)의 값이 1600으로 고정된 채 1280만 뽑아낸다면, 화면이 비스듬하게 밀리거나 깨질(diagonal tearing) 수 있습니다.
* **2단계 (Pitch 오류 발생 시 대처)**: Ghidra 구조체 추적을 발동해 인코더 동작 함수 시그니처에서 Width 외에 Row Stride 파라미터를 식별하고 이 부분도 독립 패치해야 합니다.

### 🥉 접근 D (호스트 사후 다운스케일)에 대한 견해
이 방식은 현상의 "완화"일 뿐 근본 해결책이 될 수 없습니다. ISP의 업스케일링 과정(Nearest Neighbor 혹은 Bilinear)에서 이미 오리지널 센서 데이터가 손실/왜곡되어 발생한 엣지 Aliasing은 사후 다운스케일링을 해도 어느 정도 뭉개진 흔적이 그대로 남아 있게 됩니다. Native 픽셀 단위의 샤프함을 확보하려면 펌웨어 단에서 패치가 이루어져야 합니다.

## 3. 요약된 다음 단계 액션 리스트 (Next Steps)

1. **Ghidra 검증**: `GP1235_FW.gpr` 열어서 해상도 스위치 블록 내 `Mode 3`가 Height와 파이프라인(Timestamp 등)을 어떻게 설정하는지 확인.
2. **바이너리 패치 파일 생성**: B-1번 방식의 비교점 수정 바이너리 패치 생성 (단 2바이트만/word만 교체).
3. **SPI 플래시 테스트**: `flashrom`을 사용해 패치 펌웨어를 올리고 부팅 확인 및 해상도 결괏값 확인.
