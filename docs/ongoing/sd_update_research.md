# SD 업데이트 연구 메모

> 일시: 2026-03-29
> 목적: 왜 `JH_5307.bin`으로는 원본 덤프도 실패하는지 재해석하고, SD 카드 업데이트가 성립하려면 무엇이 필요한지 정리

## 결론

현재 가장 강한 가설은:

1. SD 업그레이드 파일명은 단순히 `JH_5307.bin`이 아니라 `JH_5307*.bin`의 `*` 부분에 **8자리 ASCII 체크값**이 들어간다.
2. 업그레이드 루틴은 그 8자리를 `strtoul(..., 16)` 류 함수로 파싱해 기대값으로 사용한다.
3. 그래서 원본 SPI 덤프를 그냥 `JH_5307.bin`으로 넣으면:
   - 파일명 패턴 매칭은 통과
   - 업그레이드 루틴 진입도 통과
   - 하지만 기대 체크값 파싱이 틀어져 `Program error / Please check file`로 끝난다

즉, 현재 막힌 핵심은 "체크섬 알고리즘 미해결"만이 아니라 "업데이트 패키지 네이밍/패키징 규칙을 아직 정확히 못 맞췄다"는 쪽이 더 유력하다.

## 이 가설이 강한 이유

### 1. 실기 결과와 기존 해석이 충돌한다

이미 원본 덤프를 `JH_5307.bin`으로 넣었을 때 카메라는:

- 파일명 인식
- 업그레이드 루틴 진입
- 검증 실패 후 `Program error`

까지 갔다.

만약 기대 체크값이 진짜 파일 헤더 0x08(`0x0BD04FA2`)였다면, 원본 덤프는 적어도 포맷 면에서는 통과할 가능성이 더 높다. 그런데 실제로는 바로 검증 실패가 났다.

### 2. 바이너리 내부에는 ASCII `0BD04FA2`가 없다

원본 바이너리 내부에는 `0BD04FA2` 같은 8자리 ASCII 문자열이 없다.

따라서 `FUN_00041508`이 진짜로 "어딘가의 8바이트 ASCII hex"를 파싱한다면, 그 소스는 파일 헤더가 아니라 **파일명/검색 결과 구조체**일 가능성이 높다.

### 3. 파일명 패턴이 `JH_5307*.bin`이다

펌웨어에는 아래 문자열이 그대로 들어 있다.

- `C:\\JH_`
- `5307`
- `*.bin`

여기서 `*`가 단순 와일드카드가 아니라, 실무적으로는 8자리 hex suffix를 허용하기 위한 자리일 가능성이 높다.

가장 자연스러운 패턴은 아래 둘 중 하나다.

- `JH_5307XXXXXXXX.bin`
- `JH_5307_XXXXXXXX.bin`

## 현재 시점의 실전 전략

### 1순위: 파일명 suffix 가설 검증

원본 덤프를 아래 형식으로 여러 개 준비해 SD에서 테스트한다.

우선순위:

1. `JH_5307<값>.bin`
2. `JH_5307_<값>.bin`

후보 `<값>`:

- 헤더 0x08 값
- 파일 전체 바이트합
- 헤더 0x08 제외 바이트합
- 파일 전체 XOR32

후보 생성용 스크립트:

```bash
python3 scripts/sd_upgrade_candidates.py diagnostics/mac_analysis/firmware_backup_1.bin
```

### 2순위: "원본 통과"를 먼저 확보

수정 펌웨어를 바로 넣지 말고, 먼저 **원본 덤프가 SD 업데이트로 통과하는 조합**을 찾아야 한다.

이 단계가 통과해야 그 다음부터 수정 펌웨어도 같은 규칙으로 패키징할 수 있다.

### 3순위: 수정 펌웨어는 filename-encoded checksum 쪽으로 재포장

원본이 어떤 suffix에서 통과하면, 수정 펌웨어도 같은 규칙으로 재생성한다.

그때는 파일 본문에서 실제 검증 알고리즘이 무엇인지 다시 좁히면 된다.

## 추천 테스트 순서

1. `JH_5307<HEADER08>.bin`
2. `JH_5307<BYTE_SUM_FULL>.bin`
3. `JH_5307<BYTE_SUM_SKIP_HDR08>.bin`
4. `JH_5307<XOR32_FULL>.bin`
5. 위 4개를 `_` 구분자 variant로 반복

이유:

- 헤더 0x08은 기존 분석과 가장 직접적으로 연결됨
- 바이트합은 업그레이드 루틴에서 실제 계산된 것으로 문서화됨
- XOR32는 같은 펌웨어 계열의 부트로더 검증에 실제 사용됨

## 이 가설이 맞으면 의미하는 것

SD 업데이트가 가능하려면 필요한 조건은 다음처럼 바뀐다.

1. 파일명이 `JH_5307*.bin`일 것
2. `*` 부분이 카메라가 기대하는 8자리 ASCII hex 값일 것
3. 파일 본문 첫 부분 매직/헤더 구조가 유효할 것
4. 파일 본문에 대해 카메라가 계산한 값과 filename-encoded 기대값이 일치할 것

즉, "헤더 0x08만 맞추면 된다"보다 "올바른 업그레이드 패키지명 + 본문 검증값의 조합을 맞춰야 한다"가 더 정확한 모델이다.

## 남은 미해결

1. 8자리 ASCII hex가 정말 filename에서 오는지
2. 실제 본문 검증값이 단순 바이트합인지, 바이트합에 일부 범위/seed/필드 제외 규칙이 있는지
3. `_` 구분자가 필요한지, 아니면 바로 `JH_5307XXXXXXXX.bin`인지

## 추천 결론

지금 SD 업데이트를 살리려면 가장 먼저 할 일은 체크섬 알고리즘을 더 추상적으로 고민하는 게 아니라, **원본 덤프를 여러 suffix 파일명으로 재시험해 "업데이트 패키지명 규칙"을 먼저 확정하는 것**이다.

원본조차 `JH_5307.bin`으로 실패했다는 사실은, 현재 문제의 1차 원인이 "수정 펌웨어의 새 체크섬 미계산"이 아니라 **파일명/패키지 규칙 미충족**일 가능성을 강하게 지지한다.
