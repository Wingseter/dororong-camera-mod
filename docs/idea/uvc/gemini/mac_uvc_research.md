# UVC 호환성 문제 원인 및 해결 방안 연구 (macOS / Windows)

> **작성일**: 2026-03-29
> **배경**: `bmControls` 값을 수정하여 확장된 UVC 컨트롤(선명도, 채도, 대비 등)을 열었으나, Windows에서는 컨트롤이 조절되어도 아무런 효과가 없고, **macOS에서는 아예 인식/테스트조차 되지 않는 치명적 문제** 발생.

## 1. 원인 분석 (왜 작동하지 않는가?)

### 1.1 Firmware의 구현 누락 (근본 원인)
- 펌웨어의 `0x0822AA` 위치에 있는 `bmControls` 비트를 활성화(`0x01` → `0x3F`)한 것은 단지 **호스트 OS에게 "나는 이 컨트롤들을 지원한다"라고 광고(Advertise)한 것에 불과**합니다.
- 실제로 컨트롤 슬라이더를 움직이면 호스트 OS는 USB `SET_CUR` 요청을 카메라로 보냅니다. 그러나 **GP1235 펌웨어 내부의 USB 통신 핸들러에는 '밝기(Brightness, 0x0200)'에 대한 응답 코드만 존재할 뿐, 나머지 컨트롤(명암, 채도 등)을 받아서 실제 ISP 파라미터 메모리에 적용하는 코드가 아예 구현되어 있지 않습니다.**
- 즉, 명령을 보내도 카메라가 이를 처리하지 못해(무시되거나 STALL 오류 리턴) 아무런 효과가 없는 것입니다.

### 1.2 macOS에서 테스트조차 안 되는 이유 (Strict UVC Compliance)
- **Windows의 관대함**: Windows 기본 카메라 드라이버는 UVC 표준을 다소 느슨하게 해석합니다. 카메라가 지원한다고 거짓말(`bmControls`)을 하고 실제 정보 요청(`GET_INFO`, `GET_MIN`/`MAX`)에 오류(STALL)를 뱉어도, 경고만 띄우고 슬라이더 UI는 보여줍니다.
- **macOS의 엄격함**: macOS의 `UVCAssistant` 프레임워크는 UVC 표준을 극도로 깐깐하게 지킵니다. 장치가 연결될 때 선언된 모든 컨트롤에 대해 Probe/Commit 조회를 시도하고, **펌웨어가 하나라도 올바른 응답(최소값, 최대값, 기본값)을 주지 않으면 해당 Processing Unit(또는 카메라 전체)을 비표준(Broken)으로 간주하여 초기화를 중단(Crash)시키거나 모든 컨트롤을 아예 숨겨버립니다.** 
- 결과적으로, 펌웨어가 응답하지 못하는 빈껍데기 비트만 켰기 때문에 Mac에서는 UVC 시스템 자체가 뻗어버리는 것입니다.

---

## 2. 해결 방안 (Solutions)

현재 GP1235 저가형 펌웨어 환경에서 취할 수 있는 현실적인 접근법은 크게 두 가지로 나뉩니다.

### 방법 A: UVC 확장을 포기하고 정적 ISP 하드코딩 (권장)
UVC 동적 제어를 포기하고 카메라 자체의 기본 부팅 값을 최적화하는 "독립형 카메라(Standalone)" 연구 방향과 일치하는 가장 강력한 해결책입니다.

1. **UVC `bmControls` 롤백**: 오류의 원인이 된 `0x0822AA` 비트를 다시 `0x01`(밝기만 허용)로 되돌려 macOS와의 호환성을 정상 복구합니다.
2. **`0xC2000` 설정 블록 직접 패치**: UVC를 거치지 않고, 펌웨어 내부에 존재하는 16개의 ISP 세팅 프로파일(대비, 선명도, 채도, 감마 등)을 직접 찾아 헥스(Hex) 값으로 최적치를 영구 고정합니다.
3. 이 경우 Mac / Windows 모두에서 카메라 연결 즉시 아무런 오류 없이 최상의 화질이 출력됩니다.

### 방법 B: 펌웨어 리버스 엔지니어링을 통한 UVC 핸들러 구현 (초고난이도)
OS 화면에서 슬라이더를 움직이며 실시간 테스트를 하는 것이 **반드시 필수**라면 수행해야 합니다.

1. **USB 인터럽트 후킹**: Ghidra를 통해 펌웨어의 USB Setup Packet 핸들러 (bRequest = `0x01` (SET_CUR) / `0x81` (GET_CUR)) 코드를 리버싱합니다.
2. **어셈블리 코드 작성 및 주입**: 밝기 핸들러 코드가 위치한 곳을 찾아낸 뒤, 잉여 메모리 공간(~284KB 여유)에 명암(Contrast), 채도(Saturation) 등을 처리하는 커스텀 ARM 어셈블리 함수를 새로 작성해 점프(Jump) 시킵니다.
3. 이 커스텀 함수가 UVC로 들어온 값을 `0xC2000` 파라미터 영역이나 실제 SoC 레지스터 주소에 직접 덮어쓰도록(Write) 만들어야 합니다. 이 과정은 수많은 시행착오와 디버깅 장비(UART)가 소요되는 매우 기나긴 작업입니다.

## 결론
macOS 환경에서 발생하는 치명적인 UVC 미인식 이슈는 "펌웨어의 처리 코드 부재"와 "Apple 시스템의 깐깐한 UVC 규격 검사"가 맞물린 결과입니다.
지금 당장 시행 가능한 가장 빠른 개선(Quick Win)은 **UVC 모듈 개조(`0x0822AA`)를 원래대로 롤백하여 호환성을 되찾은 뒤, 펌웨어 내부 설정 블록(`0xC2000`)의 바이트 값 자체를 교체하는 '정적 패치' 방식**으로 화질 최적화를 속행하는 것입니다.
