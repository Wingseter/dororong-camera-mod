# Generalplus SoC (GP1235 추정) 펌웨어 보완 분석 및 향후 진행 계획

## 1. 개요
오실로스코프나 로직 애널라이저 등 하드웨어 진단 장비(찍찍이)가 없는 환경을 고려하여, **순수 소프트웨어 및 USB/SD 카드 조작만으로 실행 가능한 펌웨어 분석 및 추출 타겟**을 정리했습니다.

---

## 2. 놓친 부분 및 보완점 (소프트웨어적 접근)

### 2.1 `GPFW` 와 `GPZP` 시그니처 판단의 재고
* **현재 상태**: 디스크 스캔 중 1.86GB 및 142MB 오프셋에서 `GPZP`와 `GPFW` 패턴을 발견하였으나, 데이터의 엔트로피가 높아 압축 데이터의 우연한 일치로 간주함.
* **놓친 포인트**: **`GPFW` (GeneralPlus FirmWare)** 및 **`GPZP` (GeneralPlus Zip/Pack)**는 Generalplus SoC에서 내부적으로 사용하는 펌웨어 바이너리 리소스 및 압축 데이터의 **공식 매직 넘버(Magic Number)일 확률이 매우 높습니다**. 
* **해석**: 과거에 펌웨어 업데이트 파일을 SD 카드 최상단에 넣었다가 업데이트 후 (혹은 사용자가) 삭제했으나, 메모리가 할당 해제(디렉터리 트리에서만 지워짐)만 되고 파일 내용물은 원본 그대로 데이터 영역(Unallocated space)에 남아 있는 것일 수 있습니다.

### 2.2 부트롬(Boot ROM) / ISP 진입 모드 누락
* **현재 상태**: 웹캠(UVC) 1개, 대용량 저장장치(Mass Storage) 1개의 일반 모드 구동 디스크립터만 확인됨.
* **놓친 포인트**: 외장 SPI 플래시가 없고 펌웨어가 칩의 내부 롬에 저장되어 있다면, 제조 시 펌웨어를 최초 기록하거나 구출하기 위한 공장용 다운로드 모드(ISP 모드)가 반드시 칩 하드웨어 레벨(BootROM)에 설계되어 있습니다. 범용 기기에서는 별도의 핀 점퍼 없이 '물리 버튼'으로 이 모드 진입이 가능하도록 구성된 경우가 많습니다.

### 2.3 USB Vendor Request의 다중 검증 조건
* **현재 상태**: `bRequest`를 0x00~0xFF 범위로 순회하며 응답 없음을 확인.
* **놓친 포인트**: 기기고장을 막기 위한 안전장치로 인해 `wValue`나 `wIndex`에 특정한 "매직 암호 (`0x1234`, `0xA5A5` 등)"가 함께 전달되는 요청에만 데이터 응답을 리턴하도록 설계된 펌웨어가 흔히 존재합니다.

## 3. 향후 진행 권장 사항 (Next Steps)

하드웨어 점검이 불가능하므로, 아래 절차들로 펌웨어 확보를 위한 조치를 시도해 볼 수 있습니다.

### 진행 1. 펌웨어 잔여 데이터 확보 및 구조 추출 (우선도: 최상)
SD 카드 디스크 이미지에서 발견된 시그니처 오프셋 영역의 데이터를 실제로 추출하여 확인합니다.
* **실행 방법**: Mac 터미널(`dd` 커맨드)이나 Python 스트림 읽기를 사용하여 142MB 지점(`GPFW`) 및 1.86GB 지점(`GPZP`)부터 각각 앞뒤 약 1MB~5MB 크기의 바이너리를 잘라내 파일로 저장합니다.
* **검증 방법**: 추출한 파일을 헥스 에디터(Hex Fiend 등)로 열어서 `GPFW` 또는 `GPZP` 문자열 직후에 해당 파일 덩어리의 사이즈(Size) 정보, 빌드 일자나 버전 문자열(`Demo 1.00`), 혹은 CRC 체크섬 값 같은 연속된 헤더 구조가 나타나는지 살펴봅니다. 패턴이 명확하다면 이는 손상되지 않은 펌웨어 원본이며 추출에 성공한 것입니다.

### 진행 2. 버튼 콤비네이션으로 ISP 강제 진입 벤투 (우선도: 상)
하드웨어 분해나 납땜(디버그 핀 접속) 없이 기기를 USB 펌웨어 디버그 모드로 강제 인식시킵니다.
* **실행 방법**: 장치의 전원이 완전히 꺼진(또는 배터리 방전) 상태에서, 기기 외부의 물리 버튼(예: `사진 촬영 버튼`, `모드 전환 버튼`, `전원 버튼` 등) 중 하나를 **손으로 꾹 누른 상태를 유지하면서** Mac에 USB 선을 연결합니다. 각 버튼별로 번갈아가며 테스트합니다.
* **검증 방법**: Mac 터미널에서 `ioreg -p IOUSB` 명령어를 쳤을 때 원래 인식되던 `GENERAL - UVC` 대신, 이름이 없거나 완전히 다른 Vendor/Product ID (예: `0x1B3F:0x1628`, `0x1B3F:0x8000` 등 Generalplus BootROM 식별자)가 잡힌다면 성공입니다. 이 모드에 진입하면 Windows나 Linux의 Generalplus 펌웨어 툴로 통신을 개시할 수 있습니다.

### 진행 3. 펌웨어 업데이트 파일명 Fuzzing 시도 (우선도: 중)
이러한 저가형 SoC들은 주로 정해진 이름의 파일을 SD 카드 안에서 발견하면 자동으로 펌웨어 업그레이드 모드에 진입합니다.
* **실행 방법**: SD 카드의 루트 폴더에 짧은 테스트 문자열(예: `test`)만 들어있는 가짜 텍스트 파일을 만들고, 확장자와 이름을 다음과 같이 바꾸어 하나씩 삽입 후 기기를 부팅 시켜봅니다.
  * `GPLUS.bin`, `GPLUS_ext.bin`
  * `FIRMWARE.bin`, `rom_sd.bin`, `SPHOST.BRN`
  * `GP1235.bin`, `GPCV1235.bin`, `DP5307.bin`
* **검증 방법**: 특정 파일명을 넣었을 때 하드웨어 LED가 평소와 다르게 깜빡이거나 켜진 상태로 먹통이 된다면, 기기가 해당 파일을 "펌웨어 업데이트 파일"로 인식하고 메모리에 올리려다 (가짜 파일이므로) 에러가 난 것입니다. 올바른 파일명을 찾아내면 향후 펌웨어 패치 파일을 만들어 기보드 단에 밀어넣을 수 있는 통로가 됩니다.

### 진행 4. `TCSYSDIR` 폴더를 통한 백도어 탐구 (우선도: 중)
루트에서 확인된 `TCSYSDIR` 숨김 폴더에 구성 파일을 넣어 숨겨진 기능을 활성화합니다.
* **실행 방법**: `TCSYSDIR` 디렉터리 안에 아무 내용이 없는 `config.txt`, `engmode.txt`, `debug.txt`, `logger.txt` 이름의 빈 파일들을 강제로 생성하고 SD 카드를 기기에 마운트합니다. 영상이나 사진 촬영 작동을 몇 번 수행합니다.
* **검증 방법**: SD 카드를 PC에 다시 연결해서, 해당 폴더나 루트에 기기가 작동 중 파생시킨 로그 파일(`syslog.txt` 등)이 쓰여졌는지 확인합니다. 간혹 시스템 로그 스윕이 활성화되어 OS 내부 작동을 살펴볼 수 있습니다.

### 진행 5. 매직 넘버를 조합한 USB Vendor Request 재전송 (우선도: 하)
* **실행 방법**: Python의 `PyUSB` 탐색 스크립트를 조정합니다. `bRequest` 범위(0x00~0xFF) 탐색 프로세스를 돌릴 때, `wValue` 필드나 `wIndex` 필드에 보편적인 인증 값(`0xcafe`, `0x1234`, `0x0001`, `0xa5a5`)을 매개변수로 넣은 뒤 다시 시도해봅니다.

---

> **최종 요약**: 부가적인 H/W 프로브나 납땜 도구 인프라가 지원되지 않으므로 최우선적으로 확보해야 할 부분은 소프트웨어 상에 데이터로 잔존해있는 **SD 카드 블록(`GPFW`) 검증 추출**과 버튼 타이밍 조합을 통한 **ISP(In System Programming) 모드 트리거**입니다. 이 두 개가 가장 큰 돌파구가 될 가능성이 큽니다.
